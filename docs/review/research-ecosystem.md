# Research: Ecosystem & Reference Projects for CloserAI Benchmark

## Summary

CloserAI (a local-first, model-agnostic desktop client that hosts DeepSeek Harness as an isolated child process) sits in a well-populated reference landscape: **Open WebUI** and **LobeChat** are the mature self-hosted _web_ chat platforms with the richest feature/plugin ecosystems; **DeepSeek Harness** is the exact runtime CloserAI embeds (everything-is-a-plugin, sandbox-mode + approval-policy permission presets, append-only session log); **LM Studio** is the closed-source desktop local-model player (feature reference only); and **Cline**/**Roo Code** are the strongest sources for permission-transparency and approval-UX patterns — granular per-tool auto-approve policies, Plan/Act modes, and per-mode auto-approval categories with prominent security warnings. All claims below cite primary sources (GitHub READMEs, official docs, architecture docs).

## Project Profiles

### 1. Open WebUI (open-webui/open-webui) — feature-complete web reference

**(a) What it is + architecture.** "An extensible, feature-rich, and user-friendly self-hosted AI platform designed to operate entirely offline," supporting Ollama and OpenAI-compatible APIs with a built-in RAG inference engine. [Source: README](https://github.com/open-webui/open-webui/blob/HEAD/README.md). Installable via pip, uv, Docker, or Kubernetes; the repo layout shows a Python FastAPI-style backend (`backend/open_webui/`) with Alembic DB migrations, retrieval loaders, and many vector-DB backends (Chroma, pgvector, Milvus, Qdrant, Weaviate, etc.) plus a web frontend — i.e., a server/DB-backed multi-user architecture rather than a single desktop process. [Source: repo structure](https://github.com/open-webui/open-webui). A desktop app exists (github.com/open-webui/desktop) but the product is fundamentally web/Docker-first. [Source: docs home](https://docs.openwebui.com/).

**(b) Security/trust model.** 3-layer RBAC: **Roles** (Admin, User, Pending), **Permissions** (granular feature flags, e.g. "Can Delete Chats", "Can Use Web Search"), and **Groups** (organize users, grant additional permissions). [Source: RBAC docs](https://docs.openwebui.com/features/authentication-access/rbac/). Secure by default: signup is open only until the first user registers (who becomes admin), then auto-disabled; new accounts default to `pending` and require admin approval. [Source: hardening docs](https://github.com/open-webui/docs/blob/main/docs/getting-started/advanced-topics/hardening.md). Permissions configured via Admin Panel → Users → Groups (Default Permissions + Group Permissions). [Source: permissions docs](https://docs.openwebui.com/features/authentication-access/rbac/permissions/). This is a _web multi-user_ RBAC model — different from CloserAI's per-tool permission manifest, but a useful benchmark for scope/granularity.

**(c) Features relevant to CloserAI roadmap.** Multi-provider ("mix and match providers freely": LMStudio, GroqCloud, Mistral, OpenRouter, vLLM); plugin system (Filters, Actions, Pipes, Tools, Skills); connects external services through **MCP, MCPO, and OpenAPI tool servers**; custom agents wrapping models with instructions/tools/knowledge; persistent memory; live message flow; channels; calendar/automations. [Source: README](https://github.com/open-webui/open-webui/blob/HEAD/README.md).

**(d) Community health.** Among the most-starred self-hosted AI projects (the README leads with star/forks/watchers badges and a large active Discord). [Source: README](https://github.com/open-webui/open-webui). MIT license (repo `LICENSE`), with a commercial Enterprise plan (SLA, LTS). [Source: enterprise docs](https://docs.openwebui.com/enterprise).

**(e) Lessons.** RBAC with roles+groups+granular permission flags is the mature web-model benchmark; plugin taxonomy (Filters/Actions/Pipes/Tools/Skills) and MCP/MCPO/OpenAPI integration show how broad tool-server support scales. For CloserAI, the key takeaway is permission _granularity and default-safety_ (pending approval, secure-by-default).

### 2. LobeChat / LobeHub (lobehub/lobe-chat) — self-hosted chat platform

**(a) What it is + architecture.** Now positioned as "LobeHub … Chief Agent Operator" that "hires, schedules, reports on your entire AI team" — agents as the unit of work. [Source: README](https://github.com/lobehub/lobe-chat/blob/next/README.md). A Next.js/React-based app, self-hosted via Docker, Vercel, Zeabur, Sealos, or Alibaba Cloud; a **Plugins Gateway** backend service (deployed as a Vercel Edge Function at `POST /api/v1/runner`) serves the plugin system. [Source: chat-plugins-gateway](https://github.com/lobehub/chat-plugins-gateway).

**(b) Security/trust model.** Not a code-agent permission model like Cline/Roo; focus is org/team collaboration and access control rather than per-tool approval. Multi-instance and auth are covered in the repo's dev docs. [Source: README/repo](https://github.com/lobehub/lobe-chat). Relevant to CloserAI primarily as a multi-user/team UX benchmark, not a permission-manifest reference.

**(c) Features relevant to roadmap.** Multi-provider + multi-modal ("any model and any modality"); a claimed "10,000+ Skills" library of tools and MCP-compatible plugins; **MCP Plugin one-click installation** and an **MCP Marketplace**; Agent Builder auto-configuration; Agent Groups for parallel collaboration; scheduling; project organization. [Source: README](https://github.com/lobehub/lobe-chat). This is the strongest reference for _MCP marketplace/one-click install UX_ — directly relevant to CloserAI's MCP management UI.

**(d) Community health.** Large, actively-released open-source project (release/docker/contributor/star badges in README; Product Hunt and Trendshift badges). [Source: README](https://github.com/lobehub/lobe-chat). Open-source license (MIT). Desktop app exists too. [Source: README](https://github.com/lobehub/lobe-chat).

**(e) Lessons.** A marketplace + one-click-install for MCP/plugins is a proven way to grow a local-AI ecosystem; treating "agents as units of work" with shared contexts (Pages, Project) informs CloserAI's session/workspace UX. Note LobeHub is under active development (explicitly "active development, feedback welcome"). [Source: README](https://github.com/lobehub/lobe-chat).

### 3. DeepSeek Harness (deepseek-ai/deepseek-harness) — the runtime CloserAI hosts

**(a) What it is + architecture.** "An open-source agent harness developed by DeepSeek AI," using an architecture where **everything is a plugin**, powered by Cordis (a plugin framework where "plugins contribute services, typed events, and reversible effects to a shared context"). There is "no privileged core to patch: you extend dsh by mounting a plugin beside the others." [Source: README](https://github.com/deepseek-ai/deepseek-harness) and [Source: architecture.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md).

- **Profiles & bundles:** a running `dsh` is a plugin tree composed at boot from ordered layers. A _profile_ lists the bundles it stacks, holds out-of-tree plugins, and keeps `cordis.patch.yml`; `web` and `headless` ship as templates. `dsh-base` (model adapters, tools, persistence, sandbox+approval policy, settings, credentials, telemetry) is the first layer of every profile; `dsh-web-app` adds the browser app; `dsh-headless` is a one-shot runner. [Source: architecture.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md).
- **Sessions:** an append-only `SessionEvent` log + in-memory store (`ctx.sessions`); "Model-visible means logged" — anything reaching a model request must be reconstructable from the log. [Source: architecture.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md).
- **Tools & sandbox:** a scoped tool registry and guarded execution pipeline (`ctx.tools`); a `ctx.sandbox` backend confines spawned processes; `ctx.fs` provides filesystem access/policy. [Source: architecture.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md).

**(b) Security/trust model.** The **permission-preset** layer bundles the two enforcement knobs — **sandbox mode (`sandbox/mode`)** and **approval policy (`approval/policy`)** — into named presets exposed to clients as one Permissions selector. Defaults are `workspace-write` (workspace-write + ask) and `danger-full-access` (danger-full-access + never). This is an _optional_ capability, not part of the agent-loop spine — execution, prompt narration, and replay keep reading their knob folds independently. [Source: permission-presets docs](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/permission-presets) and [Source: package README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/interaction/permission-presets/README.md). This is the exact model CloserAI's per-mode tool-permission manifest builds on.

**(c) Features relevant to roadmap.** Multi-provider model adapters (`ctx.llm`); tools registry; sessions (fork/resume/transcripts/telemetry/persistence all derive from the session-event stream); subagents with swappable providers; an **Experimental Agent Teams** seam (durable roster, task board, mailbox over continuable subagents); `ctx.commands` (human commands without a model turn); `ctx.jobs` (background work); `ctx.goals` (same-session objectives). [Source: architecture.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md).

**(d) Community health & versioning.** MIT licensed. **Currently in "developer preview" and iterating rapidly — "THERE WILL BE COMPATIBILITY-BREAKING CHANGES."** [Source: README](https://github.com/deepseek-ai/deepseek-harness). Runs via `npx @deepseek-ai/dsh web` (Web UI at `http://127.0.0.1:3080` by default). [Source: README](https://github.com/deepseek-ai/deepseek-harness). Plugin discoverability via the `dsh-plugin` GitHub topic and a Discord community. [Source: README](https://github.com/deepseek-ai/deepseek-harness).

**(e) Lessons / risks for CloserAI.** Because DSH is in developer preview with breaking changes, CloserAI must **pin the exact DSH version** (consistent with AGENTS.md) and isolate it as a child process to absorb breakage. Extend via presets/plugins/compat layer, never fork the core. The permission-preset design (sandbox + approval as independent knobs, surfaced as one selector) is the natural foundation for CloserAI's per-mode permission manifest + approval prompts.

### 4. LM Studio — local desktop AI (closed source; feature reference only)

**(a) What it is + architecture.** A closed-source desktop application for running and serving local LLMs, plus `llmster` (a headless daemon) and `lms` (a CLI). The "LM Studio ecosystem is built around a unified core capable of model management, inference orchestration, and API serving," wrapped by the Desktop GUI or headless components. [Source: DeepWiki component overview](https://deepwiki.com/lmstudio-ai/docs/1.3-lm-studio-llmster-and-lms-component-overview). Provides TypeScript (`lmstudio-js`), Python (`lmstudio-python`), REST, and OpenAI/Anthropic-compatible endpoints; the Developer tab starts a local API server on localhost or the network. [Source: developer docs](https://lmstudio.ai/docs/developer) and [Source: server docs](https://lmstudio.ai/docs/developer/core/server).

**(b) Security/trust model.** Single-user local tool; no agent permission/approval model. It serves models locally with user control over what runs on their machine. Not a permission-UX reference. [Source: server docs](https://lmstudio.ai/docs/developer/core/server).

**(c) Features relevant to roadmap.** Local-first serving; stateful REST API with **local MCPs** (`/v1/chat`); OpenAI/Anthropic-compatible endpoints so external tools can point at it; headless deployment (`llmster`) and CLI (`lms`). [Source: 0.4.0 blog](https://lmstudio.ai/blog/0.4.0). This validates CloserAI's local-first + OpenAI/Anthropic-compatible + MCP direction. [Source: developer docs](https://lmstudio.ai/docs/developer).

**(d) Community health.** Closed source / proprietary — not a GitHub open-source project; growth driven by the product's local-model popularity rather than a public OSS community. Treat as feature reference only, never for licensing or internal reuse. [Source: developer docs](https://lmstudio.ai/docs/developer).

**(e) Lessons.** A desktop app can deliver a polished local-first experience (model management + serving + SDKs + MCP) without being open source; for CloserAI the takeaway is the SDK/API surface (OpenAI/Anthropic-compatible + REST + SDKs) and local-MCP serving pattern, not the licensing model.

### 5. Cline (cline/cline) — permission-transparency / approval-UX reference

**(a) What it is + architecture.** "The open source coding agent in your IDE and terminal" — a shared agent engine exposed as: VS Code extension, JetBrains plugin, **CLI** (interactive/headless), **Kanban** (web-based multi-agent task board), and an **SDK** (`@cline/sdk`, `npm install @cline/sdk`) powering all of them. [Source: README](https://github.com/cline/cline). Supports Plan/Act modes: "In Plan mode, Cline explores your codebase… switch to Act mode and Cline executes the plan. Every file edit and terminal command requires your approval." [Source: README](https://github.com/cline/cline).

**(b) Security/trust model — the key reference for CloserAI.** Per-tool permission policies control "whether tools are enabled and whether they run without approval." Options: `{ autoApprove: true }` (execute immediately), `{ autoApprove: false }` (wait for approval), `{ enabled: false }` (tool disabled, model won't see it); note "tool names not listed in `toolPolicies` default to enabled and auto-approved, so set policies explicitly for tools that need review." [Source: Cline permission-handling docs](https://docs.cline.bot/sdk/guides/permission-handling). Higher-level patterns documented: **Auto-Approve Everything** (trusted CI/sandbox), **Interactive Approval** (custom approval handler for human oversight), **Tiered Permissions** (auto-approve reads, require approval for writes), and **Conditional Approval** (approve based on what a tool does, not just which tool). On rejection, "the agent receives a rejection message and can adjust its approach" — it doesn't get stuck. [Source: Cline permission-handling docs](https://docs.cline.bot/sdk/guides/permission-handling). Human-in-the-loop approval + auto-approve toggle is the core UX. [Source: README](https://github.com/cline/cline).

**(c) Features relevant to roadmap.** Works with every provider (Anthropic, OpenAI, Gemini, OpenRouter, Bedrock, Azure/GCP, Cerebras/Groq, Ollama/LM Studio, any OpenAI-compatible); MCP servers (`cline mcp`) and SDK plugins; multi-agent teams (coordinator + specialists, persistent state); scheduled agents (cron); messaging integrations (Telegram, Slack, Discord). [Source: README](https://github.com/cline/cline).

**(d) Community health.** Major open-source project (Apache-2.0, active releases across SDK/CLI/extensions via GitHub workflows; large Discord/Reddit). [Source: README](https://github.com/cline/cline).

**(e) Lessons.** Cline is the strongest concrete source for CloserAI's permission-transparency: per-tool auto-approve/disable policies, tiered (read vs write) auto-approval, conditional approval by action, explicit opt-in auto-approve, and graceful agent behavior on rejection. The default-to-auto-approved caveat is a cautionary lesson — CloserAI's per-mode manifest should default to explicit/restrictive rather than implicit allow.

### 6. Roo Code (RooCodeInc/Roo-Code) — per-mode approval-category reference

**(a) What it is + architecture.** An open-source VS Code AI coding agent with a **modes** system (e.g., architect/coder); each mode has a `roleDefinition` (identity/expertise injected at the top of the system prompt), a `description`, and `whenToUse`. [Source: custom-modes docs](https://roocodeinc.github.io/Roo-Code/features/custom-modes).

**(b) Security/trust model.** Auto-approval is per-_category_: `AutoApprovalState` types include `alwaysAllowReadOnly`, `alwaysAllowWrite`, `alwaysAllowMcp`, `alwaysAllowModeSwitch`, `alwaysAllowSubtasks`, `alwaysAllowExecute`, `alwaysAllowFollowupQuestions`. [Source: src/core/auto-approval/index.ts](https://github.com/RooCodeInc/Roo-Code/blob/137d3f4f/src/core/auto-approval/index.ts). The docs carry a prominent **SECURITY WARNING**: "Auto-approve settings bypass confirmation prompts, giving Roo direct access to your system. This can result in data loss, file corruption, or worse. Command line access is particularly dangerous… Only enable auto-approval for actions you fully trust." Users enable auto-approve via the Auto-Approve dropdown next to the chat input. [Source: auto-approving-actions docs](https://roocodeinc.github.io/Roo-Code/features/auto-approving-actions/). There is active discussion of making auto-approve per-mode rather than global ([issue #12002](https://github.com/RooCodeInc/Roo-Code/issues/12002)), and bugs around mode-switch auto-approval ([issue #12001](https://github.com/RooCodeInc/Roo-Code/issues/12001)).

**(c) Features relevant to roadmap.** MCP tool support; mode-based permission separation; per-category auto-approval granularity; prominent in-UI security warnings. [Source: auto-approving-actions docs](https://roocodeinc.github.io/Roo-Code/features/auto-approving-actions/).

**(d) Community health.** Open source (Apache-2.0), active issue tracker with detailed enhancement/bug discussions. [Source: repo](https://github.com/RooCodeInc/Roo-Code).

**(e) Lessons.** Roo's per-_category_ auto-approve (read/write/MCP/execute/subtasks/mode-switch) and per-_mode_ separation map closely to CloserAI's per-mode tool-permission manifest. The explicit security warnings and the desire for per-mode (not global) auto-approval are direct UX lessons: make auto-approval scoped, visible, and default-restrictive.
